# PWA and offline caching

Decision: [ADR 0014](decisions/0014-service-worker.md). This page records what the shipped service worker does today; downstream tickets extend it.

## Install manifest

`/manifest.webmanifest` is generated by `src/app/manifest.ts` at request time. It uses the validated stored couple names, a short initials label, the active light theme primary colour for `theme_color`, and its background colour for `background_color`. The existing in-page viewport colours still follow the device appearance setting; a manifest has no equivalent device-scheme selection. Next adds the manifest link automatically.

App identity, scope and start URL are all `/`, with `display: standalone`. Neither an invitation token nor a staff session is embedded in this public document. A guest opens their personal invitation from its original link; an installed launch does not magically identify that guest. TICKET-107 supplies the explicitly authorized offline pass described below.

A separate scanner start URL was considered. For now there is one stable app identity and a public home launch; switching the same manifest between guest and scanner destinations would produce ambiguous install/update behavior. Any future separate staff install should have its own explicit identity/start URL and authentication boundary, not depend on cookies in this manifest. Scanner authorization and offline preparation are supplied by TICKET-031/032/108; the authorized scanner exception is described below.

Names are read on each manifest request, with a two-second failure boundary and sanitized warning before using the approved default names. Theme reads retain the existing tagged cache: ordinary database changes become visible after its30-second revalidation; the authorized activation service expires its tag. Browser/OS refresh of an already-installed app is outside the server cache guarantee. No private-route failure is converted into authorization by these public-branding fallbacks.

TICKET-104 generates themed192/512 any/maskable PNGs, an180px Apple touch icon and common-size Apple startup images. See public/icons/README.md for regeneration, exact dimensions and static-branding limitations. These metadata/assets alone do not prove physical installation. TICKET-113 checks manifest, icons, HTTPS, worker control and offline behavior; TICKET-114 records actual iOS/Android installs on staging HTTPS. Both downstream checks remain mandatory and are not certified by TICKET-103. No removed Lighthouse PWA audit is required. Lighthouse performance/accessibility checks are separate.

## Service worker

- Served by `src/app/sw.js/route.ts` at `/sw.js` with `Content-Type: application/javascript`, `Cache-Control: no-cache, no-store, must-revalidate` and `Service-Worker-Allowed: /`. Rendered per request (`connection()`), so no prerendered copy with framework cache headers exists.
- Registered at scope `/` with `updateViaCache: "none"` by `ServiceWorkerRegistration` in the root layout, **in production builds only**. Development never installs a worker.
- The fetch rules are `cachePolicy` in `src/modules/shared/lib/sw-policy.ts`. `/sw.js` embeds that exact function, so unit tests and the browser run the same code.
- **Install** precaches the offline page `/offline` into `wedding-offline-v1` (required: install fails and retries on the next visit if it cannot be fetched). It also precaches the build assets that page references, plus fonts referenced by its CSS, into `wedding-static-v1` (best-effort: a missing asset never fails the install).
- **Offline fallback:** a same-origin page navigation goes to the network as normal. Only when the network fails does the worker answer with the precached offline page, at the URL the guest tried, with a "Try again" button that reloads it. The visited invitation document is never stored; the explicit minimal own-pass and scanner exceptions are described below. `fetch()` calls are not navigations, so private routes such as `/admin` still fail offline.
- No automatic `skipWaiting`: a new version waits until tabs using the old one close. TICKET-111 adds the update prompt.
- Generic public-asset caching is best-effort: a hit is served from cache, otherwise the network response is returned immediately and a copy is stored in the background (`event.waitUntil`). Only complete `200` same-origin responses are stored (never `206` partial range responses), and any Cache Storage error (quota, private mode, eviction) falls back to the network instead of failing the request.
- Caches are named `wedding-<kind>-v<SW_CACHE_VERSION>`. On activate, only obsolete public `wedding-` caches are deleted; the current explicitly authorized own-pass and scanner-build caches are retained. Scanner activation invalidates an incompatible saved scanner grant before deleting its old assets; private guest snapshots are erased with incompatible scanner authority, while unsynced queues are never touched. Bump `SW_CACHE_VERSION` when cached content or layout changes.

## Authorized own-pass copies (TICKET-107)

Opening a real accepted invitation starts an explicit save request through a MessageChannel. Only a same-origin window whose URL exactly matches the canonical `/i/<capability>` may request that copy. The worker independently fetches `/i/<capability>/offline-pass`; the server rechecks current accepted status, RSVP, seats and token version through the same issuance boundary as the online pass. Only a 200 response bearing the server's own-pass marker is eligible. No invitation document, RSVP form, dietary/contact data or arbitrary authenticated response is cached.

The dedicated `wedding-own-pass-v1` store is keyed by the exact capability URL. There is no first-entry fallback or discovery link on another guest's generic offline page. Opening a signed `/p/*` URL (for example on a scanner or someone else's phone) does not authorize saving a private invitation. Query/RSC/prefetch/mutation requests do not enter the own-pass navigation path.

The saved HTML contains a read-only signed QR, name, party size, table and UTC refresh timestamp. Existing public CSS/font assets are precached from a strict same-origin build-asset allowlist; no framework hydration or editing action is included in the snapshot. The offline screen labels itself as a possibly stale copy and makes no admission guarantee. Refresh and reconnection retry the original invitation. A confirmed 401/403/404/410 response removes that capability's copy; transient outages preserve it. Saves/removals serialize per capability so a slow save cannot repopulate a known-revoked copy. Different capabilities remain isolated.

The live saved hint appears only after Cache Storage accepts the write. Quota/storage failure leaves the online QR usable with screenshot-backup advice. Browser eviction yields the generic offline page. The private cache is explicitly retained during ordinary public-cache activation cleanup. Private pass retention and storage-loss behavior are described below; offline validity is bounded, never indefinite.

Existing installed workers still follow the no-auto-skipWaiting lifecycle: close old controlled tabs to activate this version. Until an old worker can answer the new save request, no saved-success claim is made. Physical iOS/Android WhatsApp, storage lifecycle and scanner checks remain release-gated; desktop offline emulation is not device certification.

A changed token version invalidates the old saved QR before a replacement write is attempted, including when storage quota prevents the new save. If deletion fails, the worker attempts an empty durable tombstone. When both writes fail it reports unavailable and masks the known-invalid copy for that worker lifetime; durable cleanup under a completely unavailable storage API cannot be guaranteed. This limitation remains explicit: no browser code can guarantee physical deletion while every storage API rejects writes. Expired copies nevertheless fail closed on every read, including after a worker restart.

## Authorized scanner shell (TICKET-108)

A live gate session at `/checkin` prepares a minimal scanner document through
`/checkin/offline-shell`. The worker fetches it independently; window messages cannot
supply a grant, HTML or expiry. Both the proxy and endpoint explicitly deny missing,
wrong-role or expired access. Live server checks also cover revocation and credential
version. The document contains no staff name, raw cookie, form action or Flight state.
A domain-separated HMAC fingerprint is a comparison identity, not an authentication token.

`pnpm build` first generates content-addressed scanner/decoder JS, shared CSS and local
font files under ignored `public/scanner-assets/`. The final manifest is traced into
both the endpoint and worker routes. Missing/invalid manifests make `/sw.js` unavailable
rather than installing a mismatched worker. Deploy the complete generated output;
never combine a worker from one build with another build's asset inventory.

Only a query-free same-origin `/checkin` navigation receives this fallback. Required
assets live in `wedding-scanner-assets-v1-<build>`; the private grant lives separately
in IndexedDB `wedding-scanner-shell-v1`. Preparation validates every asset and reads
all of them back before publishing readiness. A missing asset, invalid/expired grant
or unavailable storage gives the generic offline page. RSC/prefetch and check-in API
requests do not receive private HTML. TICKET-065 adds the separately authorized private guest snapshot described below.
The shell does not implement TICKET-066/180's admission outbox.

The expiry is the earliest signed-cookie, current event and PIN deadline. Initial
camera mounting reconciles durable session/build identity and clamps to the earlier
deadline. Expiry and known invalidation stop camera tracks. A newly authorized session
can remain usable online even when downloading its offline assets fails; stale sessions
close. Nothing can extend a session from a timestamp supplied by the browser.

Preparation, invalidation, activation and status/document reads share an origin-wide
Web Lock across worker versions. Storage generation tokens prevent stale publication;
network preparation has a ten-second deadline including response-body consumption.
Unsupported coordination fails offline use closed. Ordinary public asset requests
cannot publish authorization or repopulate scanner readiness on their own.

Enhanced sign-out invalidates saved access before and after the server clears its
cookie, closing the reauthorization gap with another tab. Native navigation POSTs
to `/checkin` run once under the same lock and invalidate after their response (or
bounded failure), so correctness does not depend on an additional redirect fetch.
Navigating to `/staff` also relinquishes saved gate access. No mutation is cached or
replayed. A failed IndexedDB invalidation locks current tabs and removes only scanner
readiness caches across builds; guest passes and unsent scans remain untouched. If
both durable storage channels fail, successful removal is not acknowledged and durable
restart safety cannot be guaranteed.

Checks include real emitted-worker/decoder tests in Chromium and WebKit, complete
browser restarts with persistent profiles, injected storage failure/recovery, and an
authenticated Next production journey. Physical installed iOS/Android scanner operation
remains mandatory in TICKET-114; this does not certify remote revocation while a device
is offline or physical camera conditions. See `docs/reviews/TICKET-108/` for evidence.

## Private scanner guest snapshots (TICKET-065)

After sign-in, the worker fetches `/api/checkin/guest-snapshot` with the current staff cookie. The endpoint validates gate access before and after a repeatable-read projection and returns a bounded, no-store document. Only names, invitation ID/version/status, RSVP allowance, admitted count, table and public verification keys are included. Contacts, dietary/RSVP notes, credentials and signed bearer links are excluded.

The private `wedding-scanner-guests-v1` IndexedDB store is separate from public assets and admission queues. Every read/refresh/erase shares the scanner publication Web Lock and reconciles current shell identity, readiness and deadline. Generation checks defeat late writes. Sign-out, expiry, session replacement and newly shortened authority erase the private copy. Failed erasure locks offline access and removes scanner readiness across builds; all parallel erasures settle before the lock is released. Older workers' generic removal replies require locked direct cleanup.

The list refreshes every five minutes, on resume/reconnect and after known authoritative guest changes or admission receipts. Known changes invalidate only the matching private copy before refresh; a failed refresh cannot return a copy already contradicted by the server. Unknown remote changes remain unknown offline. At thirty minutes the UI shows an amber age warning and a stale-result notice; scanning continues until the trusted session deadline. There is no invented maximum snapshot age.

Offline signed QR checks show valid, used, revoked, replaced or unknown results without recording entry. Reconnection never turns an already displayed cached result into an admission form. Existing uncertain live admission retries preserve their exact intent. A new online scan is required to authorize a new admission; TICKET-066 owns offline queued admission.

Evidence: `docs/reviews/TICKET-065/`, the actual authenticated snapshot browser runner and the generated-worker Chromium/WebKit suite. Automated tests include full browser restart after storage failure and physical private-data erasure; physical installed-device certification remains in TICKET-114/TICKET-163/TICKET-201.

## Private retention and storage recovery (TICKET-184)

The own-pass endpoint attaches `X-Wedding-Offline-Expires`, calculated from the wedding calendar date plus configured retention days at midnight in the venue time zone. A missing venue zone uses the earliest possible calendar boundary (UTC+14), expiring at most 26 hours early instead of retaining private data beyond the intended deadline. This conservative fallback is only for private-cache retention; it never establishes RSVP or staff authority. Invalid nonempty zones fail the save safely. Past deadlines return 410.

The worker never returns a missing, malformed or expired-header pass offline. On own-pass access or refresh it sweeps expired entries, rereading each under its per-pass lock before removal. Legacy saves without a deadline must be saved again online. Physical removal runs when the browser executes worker activity; a closed browser cannot be promised to wake precisely at the deadline. Failed deletion cannot make an expired response readable.

Scanner logout, expired authority and private-snapshot invalidation remove acknowledged receipt copies while preserving pending/rejected attempts and refresh barriers. No private dietary notes, raw session cookies or signing keys are introduced. The existing signed authority deadline still governs scanner access; retaining evidence is not permission to keep admitting people.

An independent Cache Storage identity marker and IndexedDB journal identity detect partial eviction. IDB loss with a surviving marker, conflicting identities or interrupted initialization makes readiness and admission unavailable instead of inventing an empty journal. Cache-only marker loss is repaired only from an intact validated journal. Compatible legacy journals retain their original records when adopting the marker. Public worker cleanup retains the marker. Complete deletion of both namespaces is undetectable and cannot restore missing records; operator reconciliation and paper records remain necessary.

If storage is unavailable, stop offline admission and use the existing connection/recovery advice or supervised paper fallback. Do not clear site data, delete the outbox, or reset its marker while pending evidence may remain. Reconnect and sync while valid staff authority exists; only exact server acknowledgements permit removal. After staff authority expires, preserve the browser profile and escalate to an administrator. TICKET-231 supplies the mandatory reviewed export/import recovery path before TICKET-154 releases; that path is not implemented by this ticket. A browser fixture renewing valid authority proves preservation and ordinary sync, not post-event credential renewal or administrative recovery.

Automated evidence covers actual worker responses, capability switching/revocation, expired cached copies, partial eviction, legacy identity adoption, interrupted initialization and acknowledged-only cleanup in Chromium/WebKit. Physical phone storage behavior remains release QA under TICKET-201/TICKET-138.
