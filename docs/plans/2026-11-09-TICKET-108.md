# TICKET-108 — offline scanner shell

Root owns this worktree, started ahead of TICKET-059 from develop92451762. No database started. Keep the PR draft until059 merges and its real camera implementation is integrated.

The offline shell must survive a navigation/reload without caching arbitrary private pages or treating a cache entry as server authorization. Guest snapshots/outbox remain065/066/180; no fabricated guest results or admission writes.

1. Expose the trusted session deadline after existing live staff/device checks: minimum signed-cookie expiry, current event cutoff and current PIN expiry. Preserve the existing identity-only authentication API for all callers.
2. Save only an explicitly authorized scanner shell, bound to a server-derived session fingerprint and deadline. No raw cookies, signing keys, contacts or guest data. Worker derives authorization from an independent same-origin server request, never message-supplied expiry.
3. Preload decoder modules before declaring offline preparation ready. Require every referenced scanner/build/decoder asset to be stored successfully; enforce same-origin hashed-asset allowlists. No success message on quota, partial asset or authorization failure.
4. Canonical GET /checkin navigation only: network first; offline fallback only for the saved unexpired authorized shell. Queries/RSC/prefetch/API/admin/mutations retain current exclusions. Known logout/revocation/session replacement invalidates the copy; do not resurrect it after a concurrent save. Unsynced queues are never deleted by this shell work.
5. Keep the camera closed on reload until an explicit gesture, stop it at expiry, and show clear offline/expiry/reconnect copy. Local expiry is not server authorization; every privileged online read/write must still check the live session. Offline revocation cannot be instantaneous (ADR0020).

Verification: expiry boundary and refusal tests; exact shipped-worker VM tests for allowlist/expiry/logout/races/asset failure; real authenticated production browser offline reload with actual QR pixels and decoder asset inventory; all-theme staff accessibility/keyboard/responsive evidence. Physical phone/PWA release checks remain unverified until performed. Coordinate shared auth API with060; root owns staff-auth/staff-cookies edits. ## Reviewed implementation direction

Use a minimal standalone scanner document, not a cached copy of the full authenticated Next page. The latter includes device names, server-action forms and framework route/hydration state that should not become an offline contract. Reuse Scanner and its camera reader in a generated browser bundle; an esbuild probe of the actual059 component produced one729,926-byte output with zero external imports and zero server-module inputs. This is feasibility evidence, not browser/offline completion.

An authorized no-store endpoint should issue the minimal document and its grant together: session fingerprint, absolute deadline, build ID and server-owned asset inventory. Build the standalone JS, shared scanner CSS and local fonts before Next builds, then publish their final content-addressed manifest. Preserve existing CSP/Permissions-Policy; no raw session cookie, signing secret, server-action form or guest data in the document. Avoid Next hydration/path rewriting at/checkin.

Use a dedicated IndexedDB session record with an atomic generation check to prevent a slow save from undoing logout or session replacement, including multiple worker generations. Public hashed assets can live in Cache Storage; only publish the grant/document after all required assets succeed. Invalidation changes the persisted generation and notifies open scanner clients; unsynced queues are separate and untouched. Require expiry checks on start/read/resume as well as timers. Reject a shell if any required asset is evicted, or if its build generation is incompatible with activation cleanup.

Known limitation: offline workers cannot inspect HttpOnly cookies or discover new remote revocations; enforce known logout/replacement and server-issued expiry, and retainADR0020's explicit disconnected-device limitation. Actualbrowser tests must prove coldworkerreload, forcedfallbackpixeldecoding, missingasset/quota failure, concurrentlogout/save, sessionreplacement,200signin and expiredmetadata. No cacheentry alone authorizes an online operation.

## Prebuild deployment decision

Finalize scanner assets and manifest **before** Next builds or traces files. The
initial post-build manifest idea is rejected: installed Next standalone packaging
copies during the build, and the current Vercel adapter's post-build public-file
sync adds missing files without replacing existing placeholders. A traced mutable
placeholder can also leave stale NFT file-hash metadata. Review source:
https://github.com/vercel/vercel/blob/main/packages/next/src/index.ts#L585

The standalone shell bundles the actual Scanner/React/decoder into one browser
script, compiles the shared globals with the existing Tailwind compiler and copies
the existing full WOFF2 faces with the shared metric fallback definitions. No new
dependency. The online Next application continues to use next/font unchanged.
The native offline document needs explicit local @font-face rules because it is
not hydrated by Next; the same font files, weight ranges, swap behavior and fallback
metrics preserve the visual contract. All-theme screenshots, cold-font CLS, actual
offline decoding and physical-device release gates remain required; generator
tests do not certify them.

Literal utility candidates come from the bundled application sources. Dynamic
class-name assembly is unsupported; the real scanner surface must be visually
checked against online rendering. Every JS/CSS/font path is SHA-256 addressed.
Manifest publication follows successful asset writes. Before finishing, wire the
prebuild command and explicit tracing, then verify packaged manifest checksums.
The current generator is tested against isolated source fixtures, not yet the
production scanner entry or a Vercel deployment.
