# TICKET-204 — Follow the device light/dark setting

Replace the single `ACTIVE_THEME_ID` with a light/dark pair (`ivory-gold`, `midnight-champagne`). The registry resolves both and fails loudly if a slot holds a theme of the wrong colour scheme. The root layout stops writing theme variables inline on `<html>` (inline styles beat media queries) and instead renders one server-side `<style>`: the light theme on `:root`, the dark theme inside `@media (prefers-color-scheme: dark)`. No client JS, so the first paint is already correct. The generated CSS refuses `<` so a theme string can never close the element. The viewport gets `color-scheme: light dark` and a `theme-color` per scheme.

The guest paper layer renders when either active theme has a pattern; the dark theme already resets `--t-pattern-*`, so the texture disappears in dark mode without extra code. The global error page uses the same stylesheet. Contexts with no viewer (OG image, seed data, dev preview defaults) use the default scheme (light).

Tests: unit tests for the pair resolution and the generated CSS; e2e emulating both schemes on every route (computed colours, no inline `--t-*`, theme-color metas, pattern only in light); the 375px overflow check runs in both schemes and a tap-target check is added. Then screenshot every route at 375/768/1280 in both themes and fix the mobile issues found. Docs: theming.md and architecture.md.
