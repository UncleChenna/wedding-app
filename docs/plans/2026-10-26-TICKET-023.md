# TICKET-023 — 2026-10-26

## Contract

Implement the PRD invitation/guest/RSVP model and generated migration. Invitation tokens are unique, non-null and issued with at least 128 bits of entropy by downstream token issuance. One tag-along is the approved default; the ticket specifies a database capacity range of zero through ten. Invitation status and token version are explicit. Guest rows contain a name, optional E.164 phone, meal choice and dietary notes; the guest QR token is removed. RSVP records store attending, count and response time with one record per invitation. Preserve RLS and unrelated feature tables.

## Verification before implementation

Use the managed TICKET-023 database only (project wedding-13b237dc87ea). First confirm setup/migration completed and capture baseline counts. Add real-Postgres constraint tests with rollback isolation and explicit opt-in, including duplicate/null/short tokens, capacity limits, RSVP uniqueness and attendance counts, phone validation and removal of guest qr_token. Demonstrate failure against the old schema. Unit-only verification must not be reported as database evidence.

## Implementation and risks

Do not silently discard data or pretend a fresh-database test proves a populated upgrade. Record an ADR and any migration limitation. Seed redesign belongs to TICKET-026; only unavoidable compatibility work may accompany this schema change, with evidence.

## Completion
