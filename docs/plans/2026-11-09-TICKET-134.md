# TICKET-134 — integrated admin journey

## Goal and scope

Exercise one real authenticated setup journey on mobile and desktop: import a
small CSV, share its invitation explicitly, create a table and assign that
household, edit the menu, create a staff member/PIN and use it on a separate
staff device. Assert database effects and continuity across pages, including
all imported people sharing the assigned table. No product UI changes planned.

## Verification design

Reuse the real local email OTP/TOTP helper; no mocked admin session or bypass.
Use fresh synthetic fixture names per project/retry, a future test event date,
and local-only database identity checks. Clean only owned fixtures and restore
settings; never send external messages. Copy the synthetic invitation link in
the browser and assert the sharing event without claiming delivery.

A dedicated CI job needs an ephemeral local Supabase Auth/mail/database stack,
not just PostgreSQL. Generate its isolated configuration only in a fresh hosted
CI checkout using the existing config/template helpers, then migrate, build and
run both browser projects with per-run ephemeral signing/session material.
Existing CI gates remain unchanged. Local execution uses this ticket's managed
worktree and stack. Avoid embedding credentials in logs/artifacts or retaining
screenshots of one-time PINs. Fail closed on mismatched identity and preserve
all existing smoke/guest journey gates.

## Files and evidence

- `e2e/admin.spec.ts`: combined journey, persisted effects, cleanup.
- `scripts/test-admin-journey.ts`: opt-in runner and synthetic run identity.
- CI setup helper and focused safety tests; `.github/workflows/ci.yml` dedicated job.
- `docs/plans/TICKET-134-pr.md`: actual results, CI evidence and limitations.

Acceptance remains unchecked until the final-head admin CI job passes. Real
phone, venue and external message delivery release requirements remain separate.
