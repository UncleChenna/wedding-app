# 2026-11-01 · TICKET-183 · Resolve signed pass URLs without exposing invitation editing

**Outcome.** The QR on a guest's pass opens `/p/<signed-pass>`, a read-only page that shows the current pass state
from server data and can't edit an RSVP. This follows ADR 0020 decision 1, with signing from TICKET-056.

## Steps

1. **Eligibility rules:** `checkin/lib/pass-eligibility.ts`, a pure function from the payload and stored state to
   one of `valid`, `replaced`, `revoked`, `not-attending`, `invalid` or `unavailable`. It reports online
   eligibility only and never admission status.
2. **Pass lookup:** `checkin/server/pass-repository.ts`. It reads status, token version, RSVP count, table number
   and primary names, with no contact details, notes or dietary data.
3. **Resolver:** `checkin/server/resolve-pass.ts`. It checks the signature before any database read and logs only
   the resulting state.
4. **Page:** `checkin/components/gate-pass.tsx`, rendered by `app/(guest)/p/[pass]`.
   - Uses generic metadata, with `noindex`.
   - The proxy sends `no-store`, `no-referrer` and `X-Robots-Tag` headers.
   - A `/dev/pass` preview with sample data is used for visual review.
5. **Realistic QR length:** `shared/__tests__/qr.test.ts` now decodes a real worst-case signed pass URL in every
   theme.

## Tests

- **Unit:**
  - The eligibility matrix.
  - The resolver: signature before lookup, unavailable keys, clock skew, privacy of the result.
  - URL builders and QR size.
  - Component states: read-only, with no `/i/` links.
- **Integration (opt-in, `RUN_INVITATION_DB_TESTS=1`):** the lookup against real Postgres across the
  not-attending, valid, replaced and revoked states.
- **End-to-end:**
  - Privacy headers, the read-only forged-pass state and generic metadata.
  - Accessibility, overflow and tap targets via the route list.
- **Visual:** `/dev/pass` and `/p/invalid` in four themes at 375, 768 and 1280px.
- **Gate:** `pnpm verify`.
