Owner: divine. Branch: TICKET-185. Prerequisites were verified through the live ledger.

## Contract

Protect invitation/pass reads and staff PIN attempts across application instances.
Device cookies alone must not define the abuse identity. Keep legitimate shared
networks usable, avoid credential/IP logs, and provide uniform retry guidance.

## Implementation sequence

1. Test and implement a strict trusted-network identity helper. Only the configured
   Vercel runtime may trust its platform-provided IP header; do not infer trust
   from a client-supplied header. Reject lists, ports, zones and malformed values.
   Normalize IPv6 representations and mapped IPv4 before hashing. Local execution
   uses a fixed shared identity rather than trusting arbitrary forwarded headers.
2. Propose a PostgreSQL atomic limiter with expiring counters, database time,
   bounded cleanup and keyed identities. Preserve the existing device PIN lockout.
   Document proposed budgets and obtain required approval using synthetic results.
3. Inventory every invitation/pass entry point and enforce before sensitive lookup
   or PIN verification. Include malformed requests, metadata, downloads and actions;
   ensure no private result cache bypass and no accidental double charging.
4. Generate migrations through Drizzle, inspect SQL and request exact-path commit
   authorization. Test only the isolated stack; no production changes or new service.
5. Test two independent clients competing for the same budget, expiry, forwarded
   header spoofing, cookie replacement, legitimate shared-network traffic and
   privacy-safe unavailable/retry responses. Run quick and full verification.

## Risks and evidence

IP limits cannot prevent distributed attacks and shared NAT needs generous lookup
budgets. PIN limits require a stricter separate budget. An unavailable identity or
store must fail closed without disclosing credentials. IPv6 address churn requires
a documented network grouping policy before integration is considered complete.

<https://vercel.com/docs/headers/request-headers>. This applies to Vercel ingress,
not arbitrary self-hosted proxies. Installed Next.js headers documentation confirms
the request headers API is asynchronous and request-time only.

No rate budgets, migrations, deployment secrets, or production rollout are approved
by this plan. Physical release checks remain outstanding in their existing tickets.
