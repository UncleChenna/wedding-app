# 0014 — Explicit service-worker caching with a custom worker

- Status: Proposed for human review · 2026-10-21 · TICKET-102

**Context.** Guests need an offline pass and staff need an offline scanner without leaking household data between sessions. The app uses Next 16.4.2, React 19.3.0, Node 24, Turbopack, Cache Components and partial prefetching. Framework server caching is distinct from browser Cache Storage. Caching arbitrary HTML or React Server Component responses risks persisting personal data or replaying an incompatible response.

**Decision.** Use a small custom worker with a versioned, generated public-asset manifest and an explicit route allowlist. Keep registration in a minimal client component; serve the worker at `/sw.js`, scope `/`, with `updateViaCache: "none"`, a JavaScript content type and revalidation/no-store headers. Do not register the prototype or install a worker in normal development. TICKET-105 owns production implementation.

The worker intercepts only allowlisted same-origin GETs. Never generically cache admin pages, private API responses, arbitrary invitation URLs, POSTs, auth redirects, RSC requests or router-prefetch requests. Do not replay mutations automatically in the worker. Offline check-in uses the application-owned IndexedDB outbox, stable event IDs and reconciliation. TICKET-107 owns the authorized own-pass copy; TICKET-108 owns the scanner shell and authorized data. TICKET-184 handles expiry, logout cleanup and storage eviction. Cache entries are not authorization.

| Content                                                         | Intended policy                                                                                          | Owner              |
| --------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------- | ------------------ |
| Versioned public shell assets and offline fallback              | Precache/cache-first; content-hash manifest generated by build                                           | TICKET-105/106     |
| Explicit public menu snapshot, if a public endpoint is approved | Network-first with bounded timeout and visibly stale fallback; never reuse an authenticated response     | TICKET-105/181     |
| Own pass and scanner private data                               | Explicit authorized download, isolated identity/version and expiry; IndexedDB or dedicated private store | TICKET-107/108/184 |
| Admin, arbitrary invitation HTML, private API, RSC/prefetch     | Network-only; no generic cache fallback                                                                  | TICKET-105         |
| Check-in/order mutations                                        | Application outbox/retry with idempotency, never generic HTTP replay                                     | TICKET-066/072/180 |

**Alternatives.** The installed Next PWA guide supports a custom worker and links Serwist's Turbopack integration. Serwist remains viable: its current guide uses `@serwist/turbopack`, a generated worker route, a provider and configurable caching. The published 9.5.4 package metadata was inspected, not installed or benchmarked. Its convenience defaults include broad runtime caching and immediate activation; adopting it would still require replacing those policies and validating Cache Components integration. The webpack-oriented `@serwist/next` wrapper is not our chosen Turbopack integration. No dependency or native build was added. Revisit Serwist if asset-manifest generation or lifecycle maintenance becomes more complex than a small, reviewed implementation.

Next's experimental `useOffline` addresses connectivity and retries, not durable offline shells or application outbox reconciliation, so it does not replace the worker. Offline support must not depend on Background Sync availability, particularly on iOS.

**Lifecycle and reversal.** A new version installs its complete public cache before becoming eligible. Do not call `skipWaiting` automatically: TICKET-111 presents an update prompt, and TICKET-180 proves queued events survive activation and schema changes. Clean only application-owned, obsolete caches after safe activation; never delete IndexedDB queues during cache cleanup. Failed installation retains the previous active worker. Rollback deploys a compatible worker at the same URL, retains queue schema compatibility and tests upgrade/downgrade on a device. Removing registration alone does not remove an already installed worker.

**Validation.** `spikes/pwa/verify.mjs` copies synthetic fixtures to a temporary public directory, runs two `pnpm build` commands (baseline and prototype), launches the production server on the managed worktree's browser port and uses Chromium to verify installation, precache, runtime menu caching, offline reload and excluded private requests. It removes its temporary public files and closes its browser/server. It adds no production registration, routes, manifest or dependencies. The fixture's scope is deliberately limited to `/__pwa-spike/`; this proves the mechanism, not production route coverage. Run `node spikes/pwa/verify.mjs` in a managed worktree after dependency installation.

Measurements and full gate results are recorded in the ticket and spike README. Sequential build timings are warm-cache observations, not a benchmark. Actual own-pass privacy, root-scope matching, scanner assets, queued-event upgrades, expiry, iOS/WebKit behavior, deployed worker headers and multi-tab updates remain required acceptance work in the downstream tickets. This ADR is not evidence those features are implemented.
