# 0017 — Invitation-scoped identity and RSVP

- Status: Proposed · 2026-10-26 · TICKET-023

**Context.** The initial scaffold assigns QR tokens to individual guests and stores an RSVP enum. The PRD requires one invitation token, explicit attendance and count, named companions, and invitation status/version/seating metadata.

**Decision.** Replace the scaffold fields with the PRD model. Drizzle application inserts generate a 256-bit cryptographic base64url token; raw SQL requires a caller-supplied token. PostgreSQL enforces token uniqueness/non-null/format, tag-along capacity 0–10 (default one), positive token version, valid invitation statuses, guest name and optional E.164 phone, one RSVP per invitation and consistent attendance counts. No RSVP row means no response yet. Keep household notes and guest seating temporarily for compatibility with the existing scaffold; invitation seating is canonical for future features. Side and meal choice remain optional text until their consuming tickets define managed options.

**Migration boundary.** Migration 0001 is generated by Drizzle, with code→token and dietary_requirements→dietary_notes selected as renames. It is a prelaunch scaffold migration for an empty database: the isolated baseline had zero rows in all ten application tables. It does not backfill names, attendance or capacity for a populated old schema. Do not apply it to an existing guest database; a separately reviewed data-preserving backfill is required first. Nothing here authorizes deleting existing guest data. Applied migration 0000 remains unchanged. Downgrade requires restoring a backup and the previous application version; no destructive down migration is supplied.

**Consequences.** Guest-level QR fields disappear. Token issuance/revocation, transactional capacity enforcement and audit trails remain downstream work. RLS stays enabled with no policy changes. The seed receives only the field/response compatibility updates necessary to compile and run; TICKET-026 retains the complete seed redesign. Real constraint tests opt in with RUN_INVITATION_DB_TESTS=1, require the managed local database identity and roll back their fixtures. Normal unit tests do not imply database verification.

**Evidence.** See the TICKET-023 handoff for generated migration inspection, repeat-application counts, actual database tests and full verification. Drizzle's [generation workflow](https://orm.drizzle.team/docs/drizzle-kit-generate) owns SQL and snapshots.
